# 🎓 Studix — النظام الحالي (Overview + Support Access + Licensing)

> هذا الملف هو المرجع التشغيلي الحالي لمالك/مطوّر Studix. يوثّق الحالة **الفعلية** للكود
> اليوم فقط — لا خططاً مستقبلية، ولا ميزات لم تُنفَّذ بعد إلا إذا صُرِّح بذلك بوضوح.
> أي بند غير منفّذ اليوم مُعلَّم صراحة بعبارة **`[يحتاج تنفيذ]`** أو **"غير منفَّذ حاليًا"**.

---

## 1. Studix — نظرة عامة على النظام الحالي

**Studix** نظام إدارة مركز تعليمي (طلاب، مجموعات، حضور، امتحانات، مدفوعات، خزينة، صلاحيات...).

**البنية التقنية الفعلية:**

| الطبقة | التقنية | المنفذ الافتراضي |
|---|---|---|
| الواجهة الأمامية | React (Vite) | `5173` |
| الخادم الخلفي | Node.js + Express | `4000` |
| قاعدة البيانات | PostgreSQL عبر Prisma | — |

- عنوان الـ backend الذي تتصل به الواجهة يُقرأ من `VITE_API_URL` (متغيّر بيئة يُضمَّن وقت
  البناء عبر Vite — `src/services/api.js`)، وقيمته الافتراضية عند غيابه
  `http://localhost:4000`. النموذج المعتمَد: تطبيق محلي لكل مركز/جهاز، الواجهة والخادم
  وقاعدة البيانات على نفس الجهاز عادة، بلا reverse proxy مفترَض.
- عند كل إقلاع للخادم (`backend/src/server.js`) يُنفَّذ نظام ترحيل تلقائي
  (`backend/src/db/migrationRunner.js`) — عملية آمنة للتكرار (idempotent): لا شيء يحدث لو
  لا ترحيلات معلَّقة. تثبيت جديد كلياً يُبنى من ملف SQL حتمي واحد
  (`backend/prisma/studix-schema.sql`، يُنتَج بأداة تطوير منفصلة
  `backend/scripts/generateSchemaArtifact.js`) — لا حاجة لـ Prisma CLI ولا اتصال إنترنت
  وقت تثبيت العميل.
- هذا الإصدار من الـ README يوثّق **حصراً** نظامَي **Support Access** و**Licensing**
  (المرحلتان 4 و5) بالتفصيل — بقية النظام (الطلاب، المجموعات، المدفوعات...) خارج نطاق هذا
  المستند.

## 2. نظرة عامة على Support Access والـ Licensing

| | **Support Access** | **Licensing** |
|---|---|---|
| **الغرض** | منح مزوّد الدعم الفني وصولاً مؤقتاً ومُدقَّقاً للمساعدة/التشخيص | تفعيل النسخة المدفوعة من Studix على تثبيت عميل محدَّد |
| **من يملك المفتاح الخاص** | صاحب النظام (مقدّم الدعم) فقط | صاحب النظام (مُصدِر التراخيص) فقط |
| **أين المفتاح الخاص** | جهاز صاحب النظام فقط، خارج هذا المستودع | جهاز صاحب النظام فقط، خارج هذا المستودع |
| **ماذا يوجد عند العميل** | مفتاح **عام** فقط (`support_access_config.support_public_key`) | مفتاح **عام** فقط (`license_config.licensing_public_key`) + شهادة ترخيص موقَّعة |
| **ما يجب ألا يوجد عند العميل أبداً** | المفتاح الخاص لـ Support Access | المفتاح الخاص لـ Licensing |

كلاهما يستخدم نفس النمط الهندسي: **توقيع رقمي غير متماثل Ed25519**، بلا اتصال إنترنت،
بمفتاحين منفصلين تماماً — تسريب أو تدوير أحدهما لا يؤثر إطلاقاً على الآخر. لهذا هما زوجا
مفاتيح مستقلَّين بالكامل: مجلد مختلف، متغيّرات بيئة مختلفة، أدوات CLI مختلفة.

```text
Owner (جهاز صاحب النظام)
  │
  ├── Licensing Private Key  (~/StudixLicensing/license-private-key.pem)
  │       │
  │       ▼
  │   tools/license-issuer.js  →  License Artifact (موقَّعة)
  │
  └── Support Private Key    (~/StudixSupport/support-private-key.pem)
          │
          ▼
      tools/support-signer.js  →  Response Code (موقَّع)

────────────────────────────────────────────────────────────
Customer Installation (قاعدة بيانات العميل)
  license_config.licensing_public_key   ← يُتحقَّق به من License Artifact
  support_access_config.support_public_key ← يُتحقَّق به من Response Code
  support_access_config.installation_id ← هوية التثبيت (مصدر الحقيقة الوحيد)
```

**تدفق التحقق عند العميل (مبسّط):** التطبيق لا يملك ولا يحتاج المفتاح الخاص أبداً — فقط
يتحقق من التوقيع بالمفتاح العام المخزَّن. أي فشل تحقق (توقيع، تثبيت، منتج، انتهاء) =
"غير صالح" بلا استثناء (فشل مغلَق دائماً).

## 3. حالة التنفيذ الحالية

### Support Access

| المرحلة | المحتوى | الحالة |
|---|---|---|
| Phase 4a | Schema فقط (`support_access_config`) | ✅ مكتمل |
| Phase 4b | منطق الخادم (تحدٍّ/تحقّق/جلسة دعم) + المسارات | ✅ مكتمل |
| Phase 4c | واجهة "وصول الدعم الفني" في الفرونت-إند | ✅ مكتمل |
| Phase 4d | أدوات المالك (`support-keygen.js` / `support-signer.js`) | ✅ مكتمل |

### Licensing

| المرحلة | المحتوى | الحالة |
|---|---|---|
| Phase 5a | Schema فقط (`license_config`) | ✅ مكتمل |
| Phase 5b | منطق التحقق/التفعيل بالخادم + middleware الحجب العالمي | ✅ مكتمل |
| Phase 5c | واجهة التفعيل (Activation UI) في الفرونت-إند | ✅ مكتمل |
| Phase 5d | أداة إصدار التراخيص دون اتصال (`license-issuer.js` + `license-keygen.js`) | ✅ مكتمل |
| Phase 5e | حماية من تراجع الساعة + اختبارات نسخ احتياطي/استرجاع | ✅ مكتمل |

### ملخّص واضح لما هو منفَّذ فعلاً وما ليس كذلك

✅ **منفَّذ فعلاً:**
- Support Access (تحدٍّ/رد/جلسة/إلغاء) كاملاً.
- موقّع Support Access (`support-signer.js`) كاملاً.
- Schema الترخيص (`license_config`) كاملاً.
- تحقّق/تنفيذ الترخيص بالخادم (`requireActivation`, `getLicenseStatus`) كاملاً.
- واجهة التفعيل (Activation UI) للمدير وغير المدير.
- أداة إصدار التراخيص دون اتصال (`license-issuer.js`).
- الحماية من تراجع الساعة (`clock_high_water_mark_at`).
- سلوك النسخ الاحتياطي/الاسترجاع — **مُختبَر فعلياً** (`licenseBackupRestore.integration.test.js`).

❌ **غير منفَّذ حالياً:**
- **الإلغاء (Revocation)** لترخيص صادر بالفعل — غير منفَّذ.
- **التفعيل عبر الإنترنت (Online Activation)** — غير منفَّذ؛ كل شيء يدوي/offline.
- **بصمة العتاد (Hardware Fingerprinting)** — غير منفَّذ؛ الربط فقط بـ `installation_id`.
- **المثبِّت/التغليف (Installer/Packaging)** — غير منفَّذ؛ لا يوجد installer أو حزمة Electron في المستودع.
- **مفاتيح إنتاج فعلية** — لم تُولَّد بعد ضمن هذا المستودع (لا ملفات `.pem` هنا، ولا ينبغي أن تكون).
- **توفير المفتاح العام آلياً (Public-key provisioning)** — غير آلي؛ خطوة يدوية دائماً (انظر القسم 8).

⚠️ **موجود كبنية جاهزة لكن غير مُستهلَك بعد:**
- `requireSupportSession` (middleware) موجود ومُختبَر، لكن **لا يوجد اليوم أي مسار API آخر
  محمي به** — جلسة الدعم تُمنح وتُعرَض وتُلغى، لكنها لا تفتح أي مورد إضافي في التطبيق
  الحالي بعد.

## 4. الأدوات المتاحة (`tools/`)

```text
tools/license-keygen.js     tools/license-issuer.js
tools/support-keygen.js     tools/support-signer.js
```

لا شيء في هذا المجلد يُشحَن للعميل أو يُدمَج في بناء التطبيق — أدوات مالك فقط، تُشغَّل يدوياً
على جهاز المالك.

| الأداة | الوظيفة | مرّة واحدة أم متكرّرة | المدخلات | المخرجات | شبكة؟ | يتعامل مع مفتاح خاص؟ |
|---|---|---|---|---|---|---|
| `tools/license-keygen.js` | توليد زوج مفاتيح Ed25519 لـ Licensing | مرّة واحدة (أو تدوير متعمَّد بـ `--force`) | لا شيء (أو `--force`) | ملفا PEM (خاص+عام) على القرص + طباعة المفتاح العام فقط | ❌ لا | ✅ يُنشئه، لا يطبعه أبداً |
| `tools/license-issuer.js` | إصدار شهادة ترخيص (License Artifact) موقَّعة لعميل محدَّد | متكرّر (كل تفعيل/تجديد) | Activation Request Code + إجابات تفاعلية (License ID, Perpetual?, أيام الانتهاء, Features, Notes) | نص "License Artifact" واحد (Base64url) | ❌ لا (offline بالكامل) | ✅ يقرأه من القرص، لا يطبعه أبداً |
| `tools/support-keygen.js` | توليد زوج مفاتيح Ed25519 لـ Support Access | مرّة واحدة (أو تدوير متعمَّد بـ `--force`) | لا شيء (أو `--force`) | ملفا PEM (خاص+عام) على القرص + طباعة المفتاح العام فقط | ❌ لا | ✅ يُنشئه، لا يطبعه أبداً |
| `tools/support-signer.js` | توقيع تحدٍّ (Challenge) وارد من عميل | متكرّر (كل طلب دعم) | نص التحدّي (Challenge) | "Response Code" + وقت انتهائه | ❌ لا (offline بالكامل) | ✅ يقرأه من القرص، لا يطبعه أبداً |

> **تنبيه صريح بحسب طلب المستخدم:** لم يتم تشغيل `license-keygen.js` أو `support-keygen.js`
> أو أي أداة أخرى أثناء إعداد هذا الملف، ولم تُولَّد أي مفاتيح فعلية.

## 5. إدارة مفاتيح الترخيص (Licensing)

### مكان المفتاح الخاص افتراضياً

```text
<home directory>/StudixLicensing/license-private-key.pem
```

(يُحسَب ديناميكياً عبر `os.homedir()` في `tools/lib/licenseKeyStorage.js` — لا مسار ثابت
لأي مستخدم بعينه.)

### متغيّرات البيئة الفعلية (كما في الكود)

| المتغيّر | الوظيفة |
|---|---|
| `STUDIX_LICENSE_KEY_DIR` | يغيّر مجلد التخزين بالكامل (خاص+عام) |
| `STUDIX_LICENSE_PRIVATE_KEY_PATH` | يغيّر مسار ملف المفتاح الخاص تحديداً |
| `STUDIX_LICENSE_PUBLIC_KEY_PATH` | يغيّر مسار ملف المفتاح العام تحديداً |

### 🚨 قواعد صارمة

- المفتاح الخاص **لا يوجد أبداً** داخل هذا المستودع.
- **لا يُدمَج أبداً** داخل أي installer مستقبلي.
- **لا يُرسَل أبداً** لأي عميل.
- **لا يُرفَع أبداً** إلى GitHub أو أي مستودع.
- **لا يُطبَع أو يُسجَّل (log)** في أي مكان — كل أداة تطبع فقط المخرج النهائي الآمن (المفتاح
  العام، أو الشهادة الموقَّعة)، أبداً محتوى الملف الخاص نفسه.
- **النسخ الاحتياطي إلزامي**: فقدان هذا الملف يعني عدم القدرة على إصدار أي ترخيص جديد
  مستقبلاً لأي تثبيت يحمل مفتاحك العام الحالي — لا استرجاع ممكن سوى بتوليد زوج جديد وإعادة
  توزيع المفتاح العام الجديد يدوياً على كل عميل (انظر القسم 23).

## 7. توليد أول مفتاح ترخيص (Licensing)

**الأمر (لا تُنفِّذه فعلياً الآن):**

```bash
node tools/license-keygen.js
```

**ماذا يفعل:**

1. يولّد زوج مفاتيح Ed25519 جديد باستخدام `crypto` المدمجة في Node (بلا مكتبة خارجية).
2. يحفظ المفتاح **الخاص فقط** في المجلد المحدَّد أعلاه (صلاحيات `0600` قدر الإمكان — best-effort على ويندوز).
3. يطبع **المفتاح العام فقط** إلى الشاشة، ويحفظه أيضاً كملف منفصل.
4. **المفتاح العام آمن للمشاركة** — هذا هو جوهر التشفير غير المتماثل: معرفته لا تُتيح تزوير توقيع.
5. **المفتاح الخاص يجب أن يبقى دون اتصال ومحمياً** — هو الشيء الوحيد الذي يُميّز "أي أحد" عن "المالك الحقيقي" في القدرة على إصدار ترخيص صالح.
6. **إذا كان هناك مفتاح موجود بالفعل**: الأداة **ترفض** العمل وتخرج بخطأ (exit code 1) دون أي تعديل.
7. **سلوك `--force` الفعلي في الكود**: يتجاوز هذا الرفض ويُولِّد زوجاً **جديداً بالكامل يستبدل** الملف القديم فوراً — لا نسخة احتياطية تلقائية، ولا تأكيد إضافي داخل الأداة نفسها. يُستخدَم فقط في تدوير مفتاح متعمَّد (انظر القسم 23)، لأن أي تثبيت عميل مزوَّد بالمفتاح العام القديم سيتوقف عن قبول تراخيص جديدة موقَّعة بالمفتاح الجديد حتى تُعاد توزيعه.

## 8. توفير المفتاح العام (Public Key Provisioning)

- **أين يُخزَّن**: عمود `license_config.licensing_public_key` في قاعدة بيانات كل تثبيت عميل — فارغ (`NULL`) افتراضياً.
- **إلى ماذا يُستخدَم**: هو المرجع الوحيد الذي يتحقق به التثبيت من أي شهادة ترخيص تُلصَق في شاشة التفعيل. طالما هذا العمود `NULL`، أي محاولة تفعيل تُرفَض بحالة `not_configured` (فشل مغلَق بالتصميم).
- **هل يُوفَّر آلياً اليوم؟** **غير منفَّذ حاليًا** — لا مسار شبكة/API لهذا في أي مكان بالكود (قرار نطاق متعمَّد موثَّق في `tools/LICENSING.md`).
- **هل يُوفَّر يدوياً اليوم؟** نعم — الطريقة الوحيدة المتاحة فعلياً: تحديث مباشر لقاعدة بيانات ذلك العميل تحديداً (عبر `psql` أو Prisma Studio) بقيمة المفتاح العام (PEM) الناتجة من `license-keygen.js`.
- **هل يقوم الـ installer بذلك؟** لا — **غير منفَّذ حاليًا**، لأنه لا يوجد installer أصلاً (انظر القسم 29).
- **ما الذي يحتاج تنفيذاً مستقبلاً؟** `[يحتاج تنفيذ]` مسار توفير آلي (كجزء من التثبيت الأولي) — خارج نطاق أي مرحلة مكتملة حالياً.

نفس الكلام حرفياً ينطبق على `support_access_config.support_public_key` لـ Support Access.

## 9. الإقلاع الأول عند العميل (Customer First Boot)

عند تشغيل الخادم لأول مرة على تثبيت عميل جديد:

1. **إنشاء قاعدة البيانات**: تُبنى من `backend/prisma/studix-schema.sql` (ملف SQL حتمي واحد يُنشئ كل الجداول/القيود/الدوال) — لا حاجة لـ Prisma CLI في هذه اللحظة.
2. **`support_access_config`**: صفّ التثبيت (id=1) قد لا يكون مزروعاً في تثبيت جديد بُني من الـ schema-only dump (لا بيانات، فقط بنية) — يُنشَأ لاحقاً بشكل كسول (lazy) بأول استدعاء لـ `ensureInstallationConfig()`.
3. **`installation_id`**: يُولَّد تلقائياً عبر `DEFAULT gen_random_uuid()::text` في القاعدة نفسها، فور إنشاء هذا الصفّ — لا حساب له في كود التطبيق، وثابت بعدها بفضل trigger يمنع تعديله (`trg_support_config_installation_immutable`).
4. **`license_config`**: نفس المبدأ، صفّ id=1 يُنشَأ بشكل كسول أول مرة يُستدعى فيها `ensureLicenseConfig()` — كل الأعمدة `NULL` افتراضياً (بما فيها `licensing_public_key`).
5. **حالة التفعيل الابتدائية**: `not_configured` (لا مفتاح عام بعد) — التطبيق **محجوب** على كل `/api/*` باستثناء القائمة البيضاء (انظر القسم التالي).
6. **`GET /api/session`**: تسجيل الدخول/الخروج — **مُستثنًى** من حجب التفعيل، لأن تسجيل الدخول يجب أن يعمل حتى قبل التفعيل (كي يستطيع المدير الوصول لشاشة التفعيل أصلاً).
7. **`GET /health`**: ليس تحت `/api/` أصلاً، فهو مُستثنًى تلقائياً — يعمل دائماً بصرف النظر عن حالة التفعيل، ويُرجِع حالة الاتصال بقاعدة البيانات وعدد الجداول.
8. **بقية مسارات `/api/*`**: أي مسار آخر (`/api/students`, `/api/payments`, ...) يُرجِع **`402`** مع `{ ok:false, error, licenseRequired:true }` طالما التثبيت غير مُفعَّل — بلا استثناء، وحتى لو فشل فحص حالة الترخيص نفسه لأي سبب (فشل مغلَق حتى في حالات الخطأ).
9. **ما يراه المدير (Admin)**: شاشة تفعيل كاملة تفاعلية (زر "الحصول على رمز التفعيل" + مربّع لصق شهادة الترخيص).
10. **ما يراه غير المدير**: رسالة قيود بسيطة ("يتطلّب Studix تفعيلاً — تواصل مع مدير النظام") + زر تسجيل خروج فقط — لا قدرة على توليد رمز أو تفعيل.
11. **Support Access يبقى متاحاً**: صفحة `/support-access` مُستثناة صراحة من بوّابة التفعيل في الفرونت-إند، والمسارات `/api/support-access/*` مُستثناة صراحة في القائمة البيضاء بالخادم — تبقى تعمل بالكامل حتى على تثبيت غير مُفعَّل إطلاقاً.

**`installation_id` هو محور الهوية**: كل شهادة ترخيص تُصدَر مرتبطة به تحديداً، ولا يُخزَّن نسخة منه في `license_config` عمداً — يُقرأ دائماً من `support_access_config` مباشرة لمنع أي احتمال لانحرافه (drift).

---

## 10. رمز طلب التفعيل (Activation Request Code)

1. المدير يفتح شاشة "تفعيل Studix" (بعد تسجيل الدخول — التفعيل إجراء للمدير فقط).
2. يضغط "الحصول على رمز التفعيل" → `POST /api/license/request-code` (محمي بـ `requireAuth + requireRole('admin')`).
3. **ما يمثّله الرمز**: نص Base64url يحمل `{ v:1, installationId, product }` فقط — معلوماتي بحت، يُبلِّغ المالك بأي تثبيت ولأي منتج يجب إصدار الترخيص.
4. **هل هو سرّي؟** لا — **غير موقَّع وغير سرّي إطلاقاً**، ولا ينتهي صلاحيته أبداً. معرفته وحدها لا تُتيح لأي أحد تزوير ترخيص (فقط المفتاح الخاص يستطيع ذلك).
5. **ما يرسله العميل للمالك**: هذا الرمز فقط، كما هو.
6. **هل يمكن استخدام واتساب/بريد إلكتروني كقناة نقل؟** نعم — لأنه غير سرّي، أي قناة موثوقة بالفعل بين الطرفين تكفي.

---

## 11. إصدار ترخيص (`tools/license-issuer.js`)

**الأمر (لا تُنفِّذه فعلياً الآن):**

```bash
node tools/license-issuer.js
```

أداة تفاعلية بالكامل، **offline تماماً** (بلا شبكة، بلا اتصال قاعدة بيانات). التدفق الفعلي:

1. تطلب لصق **Activation Request Code** — تفشل برسالة واضحة لو الملف الخاص غير موجود أصلاً (توجّهك لتشغيل `license-keygen.js` أولاً).
2. تفك ترميزه وتعرض `installationId` و`product` للتأكد يدوياً.
3. **License ID**: يمكن تركه فارغاً (توليد تلقائي) أو كتابة مرجع خاص بك.
4. **Perpetual license? [Y/n]**: الافتراضي `Y` (ترخيص دائم بلا انتهاء). كتابة `n` تطلب عدد أيام الانتهاء من اليوم (رقم موجب فقط).
5. **Features**: قائمة مفصولة بفواصل، اختيارية (محجوزة لتصنيف مستقبلي — آمنة تُترَك فارغة اليوم؛ **لا تُوجَد أي أعلام/فلاغات CLI أخرى في الكود** بخلاف `--force` في أداة توليد المفاتيح).
6. **Notes**: نص حرّ اختياري (مثل اسم العميل) — مرجعي بحت، **لا يؤثر إطلاقاً** على أي تحقّق أو تفعيل.
7. الناتج: **License Artifact** — نص واحد فقط (Base64url)، بالإضافة إلى عرض License ID وتاريخ الإصدار والانتهاء (أو "Never (perpetual)").

**لا يوجد أمر "renew" منفصل** — تجديد ترخيص = تشغيل الأداة مرة أخرى بنفس رمز الطلب (أو رمز جديد) وإصدار شهادة جديدة بشروط جديدة؛ تفعيلها يستبدل القديمة بالكامل تلقائياً (لا حالة خاصة).

> **الشهادة الموقَّعة نفسها هي رمز التفعيل** — لا يوجد نظام "سيريال" قصير منفصل في هذا المشروع.

---

## 12. إرسال الترخيص إلى العميل

- **ما يرسله المالك**: نص **License Artifact** فقط، كما طُبِع من الأداة، دون أي تعديل.
- **الآمن للإرسال**: License Artifact نفسه — يثبت فقط أنه صادر عن حامل المفتاح الخاص، ولا يكشف عنه شيئاً (تشفير غير متماثل).
- **الممنوع إطلاقاً**: المفتاح الخاص، أو أي جزء منه، في أي قناة اتصال مع العميل.
- **قناة النقل**: يمكن أن تكون واتساب أو بريد إلكتروني أو أي قناة تثق بها لهذا العميل تحديداً — الشهادة مرتبطة تشفيرياً بـ `installationId` و`product` فلا فائدة عملية لاعتراضها لتثبيت آخر.

---

## 13. تفعيل العميل (Customer Activation)

1. المدير يفتح "تفعيل Studix".
2. يلصق **License Artifact** في مربّع النص، يضغط "تفعيل".
3. الفرونت-إند يرسل `POST /api/license/activate` بحمولة `{ artifact }` بلا أي معالجة تشفيرية من جانبه.
4. الخادم (`verifyAndActivateLicense` في `backend/src/lib/license.js`) يتحقق بالترتيب:
   - شكل الشهادة (payload+signature صالحان بنيوياً).
   - **التوقيع** (Ed25519 عبر المفتاح العام المخزَّن).
   - **ربط التثبيت** (`installationId` مطابق لـ `support_access_config.installation_id` الحالي).
   - **المنتج** (`product === 'studix'`).
   - **الانتهاء** (`expiresAt` إن وُجد).
   - وجود مفتاح عام مُهيَّأ أصلاً (وإلا 409 مسبقاً حتى قبل محاولة أي تحقّق).
5. عند النجاح: تُخزَّن الشهادة كاملة + الحقول المشتقّة (`license_id`, `product`, `expires_at`, `features`, `activated_at=الآن`) في تحديث واحد، **يستبدل** أي شهادة سابقة بالكامل.
6. أي فشل يُرفَض بـ `401` برسالة عامة موحّدة ("فشل التحقّق من الترخيص") — السبب الدقيق يُسجَّل فقط في `activity_logs` (`module='license'`)، لا في استجابة HTTP نفسها.

> **الفرونت-إند لا يقوم بأي تحقّق تشفيري إطلاقاً — الخادم هو المرجع الوحيد المُعتمَد** (تعليق حرفي من كود المشروع نفسه).

---

## 14. بعد التفعيل

- **ما يصبح متاحاً**: كل مسارات `/api/*` تعمل بشكل طبيعي فوراً (بحسب صلاحيات كل مستخدم كالمعتاد).
- **بعد تحديث المتصفح (Refresh)**: `ActivationGate` يعيد الفحص من الصفر عبر الشبكة عند كل تغيّر في هوية المستخدم المسجَّل (تسجيل دخول/خروج/تبديل مستخدم) — لا يعتمد أبداً على حالة محفوظة في المتصفح.
- **بعد إعادة تشغيل التطبيق (الخادم)**: لا فرق — `getLicenseStatus()` يُعيد التحقّق الكامل من الشهادة المخزَّنة في قاعدة البيانات في كل مرة، وليس من أي ذاكرة مؤقتة داخل العملية.
- **هل يلزم إنترنت؟** **لا** — التحقّق بالكامل محلي (توقيع Ed25519 يُتحقَّق منه بالمفتاح العام المخزَّن في نفس القاعدة، بلا أي اتصال خارجي).
- **هل يُعاد التحقّق من الترخيص؟** نعم — **في كل طلب محجوب** عبر `requireActivation` (middleware عالمي)، وأيضاً عند كل استدعاء صريح لـ `GET /api/license/status` — لا يُخزَّن أي قرار "مفعَّل" بشكل دائم يُعفي من التحقّق لاحقاً.
- **كيف يُكتشَف الانتهاء؟** تلقائياً، عند أول طلب بعد لحظة `expiresAt` — يعود الحجب (402) فوراً بلا أي إجراء إضافي مطلوب من أي طرف.

---

## 15. انتهاء صلاحية الترخيص

| النوع | السلوك |
|---|---|
| **ترخيص دائم** (`expiresAt: null`) | لا ينتهي أبداً، ولا تُطبَّق عليه حماية تراجع الساعة (لا يوجد انتهاء لتفاديه أصلاً). |
| **ترخيص محدود المدة** | بمجرد أن يتجاوز الوقت الحالي `expiresAt`، يعود التحقّق فشلاً (`expired`) ويُحجَب التطبيق بالكامل (402) من جديد — دون أي إجراء يدوي إضافي. |

- عند أول فحص صريح لحالة الترخيص أثناء الانتهاء (`GET /api/license/status`)، يُسجَّل حدث `license_expiration_detected` في `activity_logs` — **مرّة واحدة عبر هذا المسار تحديداً**، وليس من داخل middleware الحجب نفسه (لتفادي إغراق السجل بتكرار عالٍ).
- **Support Access يبقى متاحاً** حتى مع انتهاء الترخيص — هو مسار مستقل ومُستثنًى دائماً، وهذا بالضبط الغرض منه: إتاحة مسار لإصلاح تثبيت محجوب.
- **التجديد**: لا يوجد إجراء "تجديد" خاص — المالك يُصدِر شهادة جديدة (`license-issuer.js`) بنفس رمز الطلب أو رمز جديد، ويرسلها للعميل ليُفعِّلها من جديد. **شهادة جديدة مطلوبة دائماً** — لا آلية لتمديد الشهادة القديمة في مكانها.

## 16. الحماية من تراجع الساعة (Clock Rollback Protection)

- **لماذا يهمّ**: تطبيق offline بالكامل لا يملك مصدر وقت خارجي موثوق — تراجع ساعة النظام يدوياً قد يُستخدَم لمحاولة جعل ترخيص منتهٍ يبدو صالحاً مجدداً.
- **`clock_high_water_mark_at`**: عمود في `license_config` يخزّن أعلى قراءة زمنية (`Date.now()`) لاحظها هذا التثبيت خلال أي فحص سابق لحالة الترخيص.
- **التسامح الحالي**: `CLOCK_ROLLBACK_TOLERANCE_MS = 6 ساعات` — يغطّي بسخاء أي انتقال توقيت صيفي حقيقي (ساعة واحدة كحدّ أقصى عالمياً) وأي تصحيح NTP/يدوي بسيط، بينما يبقى صغيراً كفاية لرصد أي تراجع ذي معنى فعلي (عادة أيام/أسابيع/أشهر ليكون مفيداً لمحاولة تحايل).
- **ما يُعتبَر مشبوهاً**: الوقت الحالي أقل من (الحدّ الأعلى المخزَّن − 6 ساعات).
- **ماذا يحدث عند الكشف**: يُحجَب التفعيل (`clock_rollback_detected`) — لكن **فقط إن كانت الشهادة المخزَّنة ترخيصاً محدود المدة فعلاً** (`expiresAt !== null`). الحدّ الأعلى نفسه **لا يُخفَّض أبداً** حتى بعد كشف تراجع (لا "مكافأة" لمحاولة خفض خط الأساس).
- **لماذا يُعامَل الترخيص الدائم بشكل مختلف**: لا يوجد انتهاء يمكن الالتفاف عليه بتراجع الساعة أصلاً، فلا داعي لحجبه بهذا الفحص.
- **لماذا هذا رادع لا ضمانة تشفيرية**: تطبيق سطح مكتب offline بالكامل — مهاجم محلي متحكّم بالجهاز بالكامل يستطيع نظرياً تجاوز أي فحص ساعة محلي بحت. هذا موثَّق صراحة في الكود نفسه كـ"رادع (Deterrent)، لا ضمانة تشفيرية".

## 17. النسخ الاحتياطي والاسترجاع

بحسب السلوك **المُثبَت فعلياً** في `backend/src/lib/licenseBackupRestore.integration.test.js`:

| السيناريو | السلوك الحالي |
|---|---|
| قاعدة بيانات مُفعَّلة تم استرجاعها من نسخة احتياطية (بيانات مطابقة تماماً لِما قبل النسخ) | **تُقبَل كما هي** — نفس `license_id`، نفس `installation_id`، التفعيل يعود صالحاً فوراً دون أي إجراء إضافي. |
| قاعدة بيانات جديدة تماماً (لم تُهيَّأ من قبل) | حالة `not_configured` — يتطلّب تفعيلاً كاملاً من الصفر. |
| قاعدة بيانات استُرجعت بلا صفّ ترخيص إطلاقاً | تُعامَل كقاعدة جديدة — `not_configured`/`not_activated` بحسب الأعمدة المتاحة. |
| شهادة الترخيص (`license_artifact`) استُرجعت سليمة مع نفس المفتاح العام ونفس `installation_id` | تتحقق وتُفعَّل بشكل طبيعي — لا "وضع استرجاع" خاص، الاسترجاع غير قابل للتمييز عن "الصفّ كان موجوداً دائماً". |
| هوية التثبيت (`installation_id`) استُرجعت من النسخة الاحتياطية | تبقى نفس القيمة تماماً (immutable) — الترخيص المرتبط بها يبقى صالحاً. |

**ملاحظة مثبَّتة بالاختبار أيضاً**: الاسترجاع لا يُنشئ أبداً صفّاً مكرَّراً (singleton محمي بقيد `CHECK (id = 1)`).

## 18. إعادة تثبيت ويندوز

### الحالة أ — إعادة تثبيت ويندوز مع استرجاع قاعدة بيانات Studix

قاعدة البيانات (بما فيها `support_access_config.installation_id` و`license_config.license_artifact`) تُستعاد كما كانت تماماً → `getLicenseStatus()` يتحقق وينجح فوراً → **لا حاجة لإعادة تفعيل**.

### الحالة ب — إعادة تثبيت ويندوز مع قاعدة بيانات جديدة تماماً

`installation_id` جديد يُولَّد تلقائياً (UUID مختلف) → أي شهادة ترخيص قديمة لم تعد تطابق `installationId` الجديد (`wrong_installation`) → **إعادة التفعيل مطلوبة إلزامياً**: طلب رمز تفعيل جديد (يحمل الآن الهوية الجديدة) وإصدار شهادة جديدة له.

---

## 19. استبدال العتاد (Hardware Replacement)

- **بصمة العتاد غير منفَّذة إطلاقاً** — لا يوجد في الكود أي قراءة لمعرّف معالج/قرص/شبكة؛ الهوية الوحيدة المُعتمَدة هي `installation_id` (عمود قاعدة بيانات فقط).
- استبدال العتاد **وحده لا يؤثر على الترخيص** طالما قاعدة البيانات نفسها (بصفَّيها `support_access_config`/`license_config`) انتقلت أو استُعيدت على الجهاز الجديد — تماماً كالحالة أ في القسم 18.
- إن أُنشئت قاعدة بيانات جديدة على العتاد الجديد بدل استرجاع القديمة → نفس الحالة ب — إعادة تفعيل مطلوبة.
- **لماذا لا يوجد ربط بالعتاد عمداً**: النموذج الحالي offline بالكامل ويعتمد على قاعدة بيانات واحدة كمصدر هوية — لا حاجة معلَنة لتعقيد إضافي ببصمة عتاد ضمن هذا التصميم.

---

## 20. محدودية استنساخ قاعدة البيانات (قيد معروف ومقبول)

`installation_id` مُخزَّن في قاعدة البيانات نفسها (وليس مرتبطاً بأي شيء خارج القاعدة).

> **لذلك: نسخة كاملة مطابقة من قاعدة البيانات يمكن أن تحمل نفس هوية التثبيت ونفس الترخيص
> الصالح على جهاز آخر تماماً.**

هذا **قيد معروف ومقبول عمداً** في نموذج الترخيص الحالي (offline، بلا خادم تحقّق مركزي، بلا
بصمة عتاد) — **وليس خللاً تم تجاهله سهواً**. أي حلّ لهذا (مثل بصمة عتاد أو تفعيل عبر
الإنترنت) هو عمل مستقبلي غير منفَّذ حالياً.

## 21. Support Access — التدفق الكامل

1. **تثبيت العميل**: المدير مسجَّل دخوله بالفعل (`POST /api/session`).
2. **مصادقة المدير**: صفحة "وصول الدعم الفني" (`/support-access`) متاحة بصرف النظر عن حالة تفعيل الترخيص.
3. **توليد التحدّي (Challenge)**: ضغط "توليد رمز دعم جديد" → `POST /api/support-access/challenge` (يرفض بـ 409 فشلاً مغلَقاً لو لا مفتاح عام مُهيَّأ بعد) → nonce عشوائي (`crypto.randomBytes`) → تحدٍّ صالح لمدة **15 دقيقة** (`CHALLENGE_TTL_MS`) مرتبط بـ `installation_id` هذا التثبيت.
4. **نقل التحدّي**: يُعرَض كنص + رمز QR + زر نسخ — يُنقَل لمزوّد الدعم عبر **هاتف أو واتساب** (الواجهة نفسها تنصح صراحة بعدم استخدام البريد الإلكتروني لهذا تحديداً).
5. **التوقيع دون اتصال**: مزوّد الدعم يشغّل `node tools/support-signer.js` على جهازه، يلصق التحدّي — الأداة تتحقق من الشكل/الانتهاء محلياً قبل لمس المفتاح الخاص أصلاً — ثم يوقّعه وتُنتِج "Response Code".
6. **نقل الرد**: يُرسَل Response Code للعميل عبر نفس القناة الموثوقة.
7. **التحقّق**: العميل يلصق الرد → `POST /api/support-access/verify {challenge, response}` → يتحقق من التوقيع + ربط التثبيت + عدم الاستخدام السابق (منع إعادة استخدام nonce، بشكل متزامن يمنع سباقاً حتى لو تزامن طلبان).
8. **جلسة الدعم**: عند النجاح تُمنَح جلسة دعم لمدة **30 دقيقة** (`SUPPORT_SESSION_MAX_AGE_MS`)، بكوكي HttpOnly منفصل تماماً (`studix_support_session`) بمفتاح توقيع مُشتقّ (HMAC) مختلف عن كوكي تسجيل الدخول العادي.
9. **انتهاء/إلغاء الجلسة**: تنتهي تلقائياً بعد 30 دقيقة، أو يُلغيها المدير يدوياً فوراً ("إلغاء وصول الدعم") — كل حدث في هذه السلسلة يُسجَّل في `activity_logs` (`module='support'`).

**نقاط تصميم مهمة:**
- Support Access يستخدم زوج مفاتيح **منفصل تماماً** عن Licensing.
- يبقى متاحاً **قبل** التفعيل — بالضبط لأن الغرض منه إصلاح تثبيت عالق.
- **لا يُفعِّل الترخيص إطلاقاً** — مساران مستقلان بقرارَي ثقة مختلفين تماماً.
- كوكي جلسة الدعم **لا يمكن استخدامه كبديل لتسجيل دخول عادي** — شكل الحمولة مختلف بنيوياً (`purpose/sessionId/installationId`، بلا `id`/`role` إطلاقاً)، ومُوقَّع بمفتاح مختلف.
- **ملاحظة دقة**: `requireSupportSession` (middleware جاهز ومُختبَر في الكود) **لا يحمي اليوم أي مسار API إضافي غير صفحة الحالة نفسها** — الجلسة تُمنح وتُعرَض وتُلغى، لكن لا "قدرات دعم" إضافية مفتوحة بها بعد في هذا الإصدار.

## 🚨 22. قواعد أمنية مهمة جدًا

- ❌ لا تُرفَع أي مفاتيح خاصة إلى Git أبداً.
- ❌ لا تضع أي مفتاح خاص داخل هذا المستودع.
- ❌ لا تضع أي مفتاح خاص داخل أي installer مستقبلي.
- ❌ لا تُرسِل أي مفتاح خاص لأي عميل.
- ❌ لا تضع أي مفتاح خاص في واتساب أو بريد إلكتروني.
- ❌ لا تُنشئ أبداً "سيريال شامل/رئيسي" (Universal/Master Serial) يعمل على أي تثبيت.
- ❌ لا تُعِد استخدام مفتاح Support Access الخاص كمفتاح Licensing، ولا العكس.
- ❌ لا تُولِّد مفاتيح إنتاج فعلية أثناء أي اختبار.
- ❌ لا تُشغِّل `--force` بلا تفكير على مفتاح موجود بالفعل — كل تثبيت عميل يحمل مفتاحك العام القديم سيتوقف عن قبول أي جديد حتى تُعاد توزيعه.
- ❌ لا تُعامِل المفتاح العام كسرّ — هو آمن للمشاركة بطبيعته، إخفاؤه لا فائدة أمنية منه.
- ❌ لا تعتمد أبداً على حالة تفعيل مخزَّنة في الفرونت-إند كمرجع — الخادم وحده هو المرجع دائماً.

## 23. تدوير المفاتيح (Key Rotation)

```text
Old Private Key
      ↓
Compromise / Planned Rotation
      ↓
node tools/license-keygen.js --force   (أو support-keygen.js --force)
      ↓
توزيع المفتاح العام الجديد يدوياً على كل تثبيت عميل (تحديث تطبيق مضبوط، لا تلقائي/صامت)
      ↓
كل ترخيص جديد يُصدَر بالمفتاح الخاص الجديد فقط
```

- **ما يحدث للتراخيص القديمة**: أي تثبيت لم يستلم المفتاح العام الجديد بعد **يستمر بالعمل بشكل طبيعي** بترخيصه الحالي (لا شيء يُبطَل تلقائياً بمجرد التدوير) — التدوير يؤثر فقط على **قدرة إصدار تواقيع جديدة يقبلها ذلك المفتاح العام تحديداً**.
- **لا يوجد نظام تدوير مزدوج (Dual-Key) فعلي** — لا يوجد في الكود أي دعم لقبول توقيع بمفتاحين عامين في آن واحد؛ توفير المفتاح الجديد لكل تثبيت خطوة يدوية منفصلة لكل عميل.
- **لا "إلغاء" فعلي على المفتاح القديم نفسه** — هو ببساطة يتوقف عن كونه المفتاح الذي تُصدَر به تواقيع جديدة؛ لا آلية قاعدة بيانات مركزية لسحبه من أي مكان.

## 24. الإلغاء (Revocation)

> **الإلغاء (Revocation) لترخيص صادر بالفعل غير منفَّذ حالياً — بشكل متعمَّد ومُعلَن في وثائق المشروع نفسها.**

- **لماذا أُجِّل**: النموذج بالكامل offline بلا خادم مركزي — إضافة إلغاء حقيقي تتطلّب إما اتصال إنترنت دورياً (يتعارض مع فلسفة "offline بالكامل") أو آلية تحقّق إضافية معقّدة لم تُدرَج ضمن أي مرحلة مكتملة حتى الآن.
- **القيد الناتج**: ترخيص صالح تشفيرياً (توقيع صحيح، تثبيت مطابق، لم ينتهِ) **يبقى يعمل** حتى لو أراد المالك إبطاله لسبب تجاري (مثل توقّف عقد العميل) — الوسيلة الوحيدة المتاحة اليوم للتأثير على تراخيص مستقبلية هي تدوير المفتاح (القسم 23)، وهذا لا يمسّ الشهادة المُفعَّلة بالفعل على جهاز العميل.
- **لماذا لا توجد خدمة إلغاء عبر الإنترنت حالياً**: لم تُنفَّذ أي بنية تحتية خادم/شبكة لهذا الغرض في أي مرحلة من مراحل Licensing المكتملة (5a–5e) — قرار نطاق صريح، لا سهو.

---

## 25. العمل دون اتصال (Offline Operation)

لا يتطلّب التصميم الحالي اتصال شبكة لأي من:

- إصدار الترخيص (`license-issuer.js`).
- توقيعه (نفس الأداة، بلا استدعاء شبكة).
- نقل الشهادة (يدوي عبر أي قناة تثق بها).
- التحقّق من الترخيص (محلي بالكامل بالمفتاح العام المخزَّن).
- التفعيل نفسه (`POST /api/license/activate` يعمل بالكامل محلياً بين الفرونت-إند والباك-إند على نفس الجهاز/الشبكة المحلية — لا استدعاء خارجي).
- التشغيل المُرخَّص العادي بعد التفعيل.

الشيء الوحيد الذي يتطلّب **نقلاً بين طرفين** (لا "اتصال إنترنت" بالمعنى التقني، بل تواصلاً بشرياً) هو نقل **Activation Request Code** من العميل للمالك، ونقل **License Artifact** بالعكس — وكلاهما مصمَّم عمداً ليتم عبر أي قناة خارجية (هاتف/واتساب/بريد) لا عبر شبكة داخل التطبيق نفسه.

## 29. جاهزية الإنتاج الحالية

### ✅ منفَّذ
- Support Access (خادم + واجهة + أدوات مالك) بالكامل.
- Licensing (schema + تحقّق/تنفيذ خادم + واجهة تفعيل + أداة إصدار) بالكامل.
- الحجب العالمي على `/api/*` (`requireActivation`) fail-closed بالتصميم.
- الحماية من تراجع الساعة للتراخيص محدودة المدة.
- توليد المفاتيح (كلا النظامين) عبر أدوات CLI مخصَّصة.

### ❌ غير منفَّذ
- الإلغاء (Revocation) لترخيص صادر.
- التفعيل عبر الإنترنت (Online Activation).
- بصمة العتاد (Hardware Fingerprinting).
- المثبِّت/التغليف (Installer/Packaging) — لا يوجد installer في المستودع.
- توليد مفاتيح إنتاج فعلية — لم يحدث ضمن هذا المستودع.

### ⚙️ يحتاج خطوة تشغيلية يدوية
- توفير المفتاح العام (Licensing وSupport Access) في قاعدة بيانات كل عميل.
- نقل Activation Request Code / License Artifact / Support Challenge / Response Code — كلها يدوية عبر قناة خارج التطبيق.
- تدوير أي مفتاح خاص وإعادة توزيع العام الجديد.

### 🔮 عمل مستقبلي (خارج نطاق أي مرحلة مكتملة)
- خدمة إلغاء تراخيص.
- مسار توفير مفتاح عام آلي (كجزء من تثبيت مستقبلي).
- بصمة عتاد اختيارية لتضييق قيد الاستنساخ في القسم 20.
- Installer/Packaging فعلي.
